Bugs

- SPINNING CURSOR - MEASURED, AND IT IS device_open(): reconfigure holds configLock for up to 1437 ms and the breakdown says where (close+probe 0, rate+buffer 4, open 1432). getState(), setState() and setupProcessing() all take that lock on the HOST'S MAIN THREAD, and Ableton calls getState() for undo snapshots on ordinary UI actions - so any control that causes a reconfigure (the offset arrows do, through the latency change) blocks the host for as long as CoreAudio takes to start the device. THE SHAPE OF THE FIX: close under the lock and leave running=false; do the properties, the ring/resampler build and device_open OUTSIDE it (the audio thread already returns silence while running is false, and no IOProc exists yet to touch the ring); retake the lock only to set running=true and publish. The one cost is that a host saving DURING a swap reads the previous device, which is honest enough for a state that is mid-change. Not attempted at the end of a long session; the diagnostics that pinpoint it are in place
- A device already open elsewhere silently keeps ITS buffer size, and GenBridge's request is accepted and ignored - the panel now says so, but nothing tries to recover. Worth deciding what should happen: re-request when the other holder lets go, or say plainly on the panel that the setting cannot take effect while something else has the device. See findings 2026-09-08 (10)
- GB_AUTO_MARGIN (1.25) has never been justified by measurement - it is 6.3 ms of headroom at a 1024 frame host buffer, on top of a floor that is already the worst case. Sweep it toward 1.05 against the underrun counter and see what it actually needs; and consider exposing the manual setpoint (targetMs), which is honoured today but has no control

If that is real rather than a rig artefact it makes the honest pipeline delay genuinely larger than the setpoint implies, which is the reporting question from the other end.
